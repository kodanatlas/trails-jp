# cron の「起動したが記録前に中断」を検知できるようにする

- 日付: 2026-09-09（JST）
- ステータス: **中止**（実装・push まで完了したがユーザー判断で revert。調査結果は再挑戦のために残す）
- 関連: `2026-08-14_cron-watchdog-gh-actions.md`（watchdog 本体の移設）

## 発端

2026-09-08 19:26 UTC の `cron-watchdog`（run 34268970216）が失敗し、GitHub から通知が届いた。

```
::error::区分 A | job=sync-lapcenter | latest=2026-09-07T13:15:32.514718+00:00 age_h=30.185 max_age_h=26
```

watchdog 自身の不具合ではなく、`sync-lapcenter` の欠測を正しく検知した結果だった。

## 調査でわかったこと（この節は revert 後も有効）

| 確認項目 | 結果 |
|---|---|
| `cron_log` の 9/8 分 | `sync-lapcenter` の行が**1 行も無い**。最後は 9/7 13:15 UTC |
| 同日の他ジョブ | `sync-events`(10:19 UTC)・`sync-entries`(11:35, 17:18 UTC) は成功 → cron 全体の停止ではない |
| デプロイ | 最終コミットは 9/2。cron 付け替えによるスキップではない |
| 実行時間 | 直近は 31〜42 秒（`maxDuration = 60`）。9/7 は 31.1 秒で余裕あり |
| 実行時刻 | `vercel.json` は 12:41 UTC 指定だが、実際の記録は毎日 13:15 UTC（34 分遅延が常態） |
| `cron_log.status` | `text NOT NULL`、CHECK 制約なし。既存値は `success`(557) と `error`(3) のみ |

### 単発ではなく恒常パターン

`2026-08-14_cron-watchdog-gh-actions.md` の 60 日集計によれば、`sync-lapcenter` は
6/15・6/17・6/22・6/23・7/7・8/3 にも欠測している（60 日で 6 日 ≒ 10%）。他 2 ジョブより多い。
**繰り返し起きているのに原因が特定されていない現象**である。

### なぜ原因を特定できないのか（未解決のまま）

`sync-lapcenter` は `logCron()` を全処理の**最後**に 1 回だけ呼ぶ。
`maxDuration = 60` 秒で強制終了されると catch 節にも到達せず、記録が一切残らない。
そのため「そもそも起動しなかった」と「起動したが記録の手前で落ちた」が原理的に区別できない。

**この構造は revert により元のまま残っている。** 次に欠測しても切り分けはできない。

## 再挑戦するときに必ず踏まえること（この節が本 plan の主な価値）

1. **開始記録を素朴に足すと監視が壊れる。**
   `cron-watchdog.ts` の `failureReasons` は `status !== "success"` を失敗とみなすため、
   `started` 行が混ざると区分 A（齢）・B（連続失敗）・B2（7 日失敗数）がすべて誤作動する。
   取得段階での除外が必須。

2. **フィルタは `status=in.(success,error)` ではなく `status=neq.started`。**
   前者だと将来 `failed` 等の未知 status が入ったときにその行ごと監視から落ち、区分 B/B2 が検知漏れする。

3. **管理画面 `/admin/cron-status` も同時に直さないと退行する。**
   これは Codex の二次レビューでも見落とされ、fresh-eyes レビューで初めて見つかった。
   `fetchRecent` は status フィルタなしで取得し、`assessJobHealth` は `rows[0]` を最終実行として扱う。
   `assessJobHealth` は `status === "error"` でなければ経過時間だけで色を決めるため `started` は緑になる。

   | 中断が起きた日 | 対策前 | `started` 導入後（未対策） |
   |---|---|---|
   | `rows[0]` | 前日の success（約 27h 前） | 当日の `started`（数時間前） |
   | 判定 | 黄「24-48時間 未実行」 | **緑「正常」** |

   検知したい日にこそ警告が消える。副次的に `HISTORY_LIMIT = 30` が実質 15 日分に半減し、
   履歴テーブルは `success` 以外を赤バッジで描くため正常日にも `started` の赤バッジが並ぶ。

4. **開始記録には短いタイムアウトが要る。ただし失われたことを検知できるようにする。**
   専用の期限が無いと `supabase-admin` の共通 fetch タイムアウト（15 秒）が適用され、
   DB 不調時に 60 秒予算の 25% を開始記録だけで消費し、着手期限（`START_EVENT_BEFORE_MS = 30_000`）まで削る。
   一方で短く締めると **DB が詰まっている日ほど開始記録が落ちやすく**、DB 遅延は 60 秒キルの有力仮説そのもの。
   つまり一番知りたい日に信号が消える。`logCron` の戻り値を捨てず記録の信頼度を残すこと。

5. **未対応で残ったレビュー指摘**（再挑戦時に併せて処理するとよい）
   - `judgeStartedRun` が `completed.rows[0]` をソートせず最新とみなす（現行 URL では `order=created_at.desc` が効くため顕在化しない）
   - 区分 C の文言が「完了記録の書き込みだけ失敗」を包含していない
   - `started` を書かない 2 ジョブにも開始記録の取得リクエストを出している
   - 開始記録の日時が不正なとき無音になる（`parseCronRows` は同じ状況で区分 D を出すのと非対称）

## 中止の経緯

実装・二段レビュー・退行修正・push・CI 通過まで完了した状態で、ユーザー判断により revert した。
技術的な不備が理由ではない（CI 緑・932 テスト通過・実データ確認済み、退行も修正済みだった）。

なお `cron_log` に `started` 行が書き込まれる前に revert しているため、DB にゴミは残っていない
（初回書き込みは 2026-09-09 22:15 JST 頃の実行予定だった）。データ面の後始末は不要。
