# cron の「起動したが記録前に中断」を検知できるようにする

- 日付: 2026-09-09（JST）
- ステータス: **完了**（`0e2b573` push 済み、退行修正を追加コミット）
- 関連: `2026-08-14_cron-watchdog-gh-actions.md`（watchdog 本体の移設）

## 発端

2026-09-08 19:26 UTC の `cron-watchdog`（run 34268970216）が失敗し、GitHub から通知が届いた。

```
::error::区分 A | job=sync-lapcenter | latest=2026-09-07T13:15:32.514718+00:00 age_h=30.185 max_age_h=26
```

watchdog 自身の不具合ではなく、`sync-lapcenter` の欠測を正しく検知した結果だった。

## 調査でわかったこと

| 確認項目 | 結果 |
|---|---|
| `cron_log` の 9/8 分 | `sync-lapcenter` の行が**1 行も無い**。最後は 9/7 13:15 UTC |
| 同日の他ジョブ | `sync-events`(10:19 UTC)・`sync-entries`(11:35, 17:18 UTC) は成功 → cron 全体の停止ではない |
| デプロイ | 最終コミットは 9/2。cron 付け替えによるスキップではない |
| 実行時間 | 直近は 31〜42 秒（`maxDuration = 60`）。9/7 は 31.1 秒で余裕あり |
| 実行時刻 | `vercel.json` は 12:41 UTC 指定だが、実際の記録は毎日 13:15 UTC（34 分遅延が常態） |

### 単発ではなく恒常パターンだった

`2026-08-14_cron-watchdog-gh-actions.md` の 60 日集計によれば、`sync-lapcenter` は
6/15・6/17・6/22・6/23・7/7・8/3 にも欠測している（60 日で 6 日 ≒ 10%）。他 2 ジョブより多い。
**繰り返し起きているのに原因が特定されていない現象**である。

### なぜ原因を特定できないのか

`sync-lapcenter` は `logCron()` を全処理の**最後**に 1 回だけ呼ぶ。
`maxDuration = 60` 秒で強制終了されると catch 節にも到達せず、記録が一切残らない。
そのため「そもそも起動しなかった」と「起動したが記録の手前で落ちた」が原理的に区別できない。

## 対応

実装は Codex CLI（WSL 側 workspace-write）へ委譲。一次レビュー（Claude）→ 二次レビュー（Codex read-only）→ 指摘修正、の順で進めた。

| ファイル | 変更 |
|---|---|
| `src/app/api/cron/sync-lapcenter/route.ts` | 処理の最前で `logCron(…, "started", …, { timeoutMs: 2000 })` を記録 |
| `src/lib/cron-logger.ts` | `status` に `"started"` を追加。任意の `timeoutMs` を受け、`AbortSignal.timeout` で insert を実際に中断 |
| `scripts/cron-watchdog.ts` | 取得 URL に `status=neq.started` を付与。区分 C（中断検知、閾値 `MAX_RUNNING_H = 0.5` 時間）を追加 |
| `scripts/cron-watchdog.test.ts` | 区分 C のテスト 12 件（境界値・不正日時・同時刻・取得失敗を含む） |

### 設計上の判断

- **開始記録を素朴に入れてはいけない**。`failureReasons` は `status !== "success"` を失敗とみなすため、
  `started` 行が混ざると区分 A（齢）・B（連続失敗）・B2（7 日失敗数）がすべて誤作動する。
  取得段階で `status=neq.started` により除外し、既存判定の意味を保った。
- フィルタは `status=in.(success,error)` ではなく **`status=neq.started`**。前者だと将来 `failed` 等の
  未知の status が入ったときにその行ごと監視から落ち、区分 B/B2 が検知漏れする（二次レビュー指摘）。
- 開始記録には **2 秒のタイムアウト**を設けた。専用の期限が無いと `supabase-admin` の共通 fetch
  タイムアウト（15 秒）が適用され、DB 不調時に 60 秒予算の 25% を開始記録だけで消費し、
  スクレイプ着手期限（30 秒）も削る。DB が詰まっている日ほど本処理を圧迫するという最悪の形になるため（二次レビュー指摘）。
- 完了記録の**取得に失敗**した場合は区分 C を出さない。取得失敗は「完了記録が無い」証拠ではなく、
  正常完了したジョブでも区分 D と C が二重に出てしまう（二次レビュー指摘）。

### 採用しなかった指摘

- **開始/完了に共通の `run_id` を持たせて照合する**: このジョブは日次 1 回で同時実行・重複実行が起きない。
  中断の翌日に再実行が成功すればその中断は検知されないが、そのときは区分 A も解消しており実害がない。
  制約は `judgeStartedRun` のコメントに明記した。
- **`fetch` をモックした `main()` の URL・出力テスト**: スコープ拡大のため。判定関数のテストで代えた。

## fresh-eyes レビューで見つかった退行（M1）と追加対応

push 後に Claude の別コンテキスト（read-only）でレビューしたところ、
**Codex の二次レビューでも私の一次レビューでも見落としていた退行**が見つかった。

### M1: 管理画面が中断日を「正常」と表示してしまう

`src/app/admin/cron-status/page.tsx` の `fetchRecent` は status フィルタなしで `cron_log` を取得し、
`src/lib/cron-status.ts` の `assessJobHealth` は `rows[0]` を最終実行として扱う。
`assessJobHealth` は `status === "error"` でなければ経過時間だけで色を決めるため、`started` は緑になる。

| 中断が起きた日 | 変更前 | M1 修正前 |
|---|---|---|
| `rows[0]` | 前日の success（約 27h 前） | 当日の `started`（数時間前） |
| 判定 | 黄「24-48時間 未実行」 | **緑「正常」** |

検知したい日にこそ警告が消えるという、変更の目的と正反対の挙動だった。
副次的に `HISTORY_LIMIT = 30` が実質 15 日分に半減し、履歴テーブルは `success` 以外を赤バッジで描くため
正常日にも `started` の赤バッジが並ぶ（カードは緑・履歴は赤という矛盾表示）。

GitHub Actions 側の watchdog（メール通知の本線）は `status=neq.started` により影響を受けない。退行は管理画面に閉じていた。

**対応**: クエリ側（`fetchRecent` に `.neq("status", "started")`）と判定側（`assessJobHealth` の冒頭で除外）の
二重で防ぎ、`src/lib/cron-status.test.ts` を新規作成して退行の形をテストで固定した。

### M2: 開始記録が静かに失われても気づけない

`logCron` の戻り値を捨てていたため、開始記録が 2 秒のタイムアウトで残らなかった日を知る手段がなかった。
15 秒→2 秒に締めたことで **DB が詰まっている日ほど開始記録が落ちやすく**、
DB 遅延は 60 秒キルの有力仮説そのものなので、一番知りたい日に信号が消える構造だった。

**対応**: 戻り値を `payload.started_logged` に載せ、完走した日の記録信頼度を可視化した。
`started_logged=false` が常態化していれば 2 秒が短すぎる兆候として読める。

なお `logCron` のタイムアウトが本処理を巻き込まないことはレビューで確認済み
（postgrest-js が fetch の reject を `{ error }` に変換し、`logCron` の try/catch でも吸収される）。

  [INFO] lc_performances latest_event_date=2026-09-06

  区分 C・D は出ず、`[OK]` 行も出力されない（表示の revert が効いている）。

## 残課題

- Codex のクレジットが尽きたため（`ERROR: Your workspace is out of credits.`）、
  修正後の二次レビューは Codex ではなく Claude の別コンテキスト（read-only・fresh-eyes）で実施した。
  M1/M2 の修正自体はユーザー承認のもと Claude が直接実装している（`rules/model-policy.md` の例外運用）。
- レビューで挙がった Minor のうち、次は**未対応**（後追いで差し支えないと判断）:
  - `judgeStartedRun` が `completed.rows[0]` をソートせずに最新とみなす（現行の URL では `order=created_at.desc` が効くため発生しない）
  - 区分 C の文言が「完了記録の書き込みだけ失敗」を包含していない
  - `started` を書かない 2 ジョブにも開始記録の取得リクエストを出している
  - 開始記録の日時が不正なとき無音になる（`parseCronRows` は同じ状況で区分 D を出すのと非対称）
- 9/8 の欠測が「未起動」か「起動後の中断」かは**まだ確定していない**。
  本変更をデプロイした後に次の欠測が起きれば、区分 C の有無で切り分けられる。
- 開始記録は `cron_log` に 1 日 1 行ずつ蓄積する。現状のテーブル規模（約 560 行）では問題ないが、
  長期的には古い `started` 行の掃除を検討してよい。
