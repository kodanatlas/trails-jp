# 静的データ（public/data）を Cloudflare R2 に置く案の検討

ステータス：保留（2026-11-19 本人判断。Vercel 無料枠の実測から今は効果が小さい。下の「再検討する条件」を満たしたら再開）

## 対象
- `public/data/`（48MB）：rankings 13MB・leg-fp 27MB（ビルド時生成・gitignore）・athlete-index 1.7MB・lapcenter-runners 2.8MB・leg-fingerprint 2.2MB など
- 読み方は 2 通り
  - ブラウザの fetch（AnalysisHub・LegFingerprintCard・CrossRaceCard・AthleteStandalone・RankingView・leg-fp 明細）
  - サーバーの fs 読み込み（/a/[name]・opengraph-image・/api/athletes/*・sitemap・site-stats ほか）

## Vercel 無料枠の実測（2026-11-19・直近 30 日のローリング）
| 項目 | 使用量 / 上限 | 直近の 1 日あたり |
|---|---|---|
| CDN リクエスト | 72.7 万 / 100 万 | 約 2 千（直近 12 時間で約 1 千。上位は `/`・/results・/api/athletes。/data は上位 10 に入らない） |
| Fast Data Transfer | 10.3GB / 100GB | 直近 12 時間で 18MB |
| ISR 書き込み | 13.0 万 / 20 万 | 1 千前後（11/5 の on-demand 化以降。10/26〜11/5 は 1 万前後） |
| Fluid Active CPU | 3h16m / 4h | 4〜6 分（11/3 頃は 15 分） |
| 関数の呼び出し | 8.6 万 / 100 万 | 1〜3 千 |

30 日の合計が高いのは 10 月末〜11 月上旬の山（先読み・和文フォント・時間ベース ISR）が窓に残っているため。対策後の 1 日あたりで 30 日を見積もると、CDN 約 6 万・ISR 約 3 万・CPU 約 2.5〜3 時間。

## 判断
- R2 に移して減るのは、ブラウザが取りに来る `/data/*.json` の CDN リクエストと転送量だけ。どちらも今は上限に遠く、/data は上位にも出ない
- 上限に最も近い Active CPU は関数の実行時間で、R2 では減らない。サーバー側の fs 読み込みを R2 からの取得に変えると、かえって遅くなる
- 増える手間：Cloudflare のトークンを GitHub/Vercel のビルドに渡す・CORS・キャッシュの消し方・ビルドごとの leg-fp 世代の掃除・置き場が 2 か所になる
- よって今は移さない

## 再検討する条件
- CDN リクエストか Fast Data Transfer が、対策後の 1 日あたりで上限の 70% ペースを超えたとき
- データの更新をデプロイから切り離したくなったとき（例：ランキングを週 1 の再デプロイなしで差し替えたい）

## 代わりに見るべきもの
- Active CPU の内訳（Observability → Functions の route 別）。cron の sync-lapcenter・/a/[name] の再生成・/api/athletes/search の JSON 読み込みが候補
