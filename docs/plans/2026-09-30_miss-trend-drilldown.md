# ミスの傾向（クロスレース）: セルの根拠レッグを見せる（ドリルダウン）

- 作成: 2026-09-30 JST
- ステータス: **実装中**（設計 v3 確定・PR 1 データ生成に着手 2026-09-30）
- 前段: `2026-06-29_results-analysis-methodology.md`（§92/§247: 個別レッグに「ナビミス」と断定しない・§378 セル単位の多重性制御）／`2026-07-07_stage2b_miss_fingerprint.md`（現行カードの統計スペック）

## 1. 目的

`LegFingerprintCard` の 3×3 セル（局面×レッグ長）や重大度ビンの割合が、**どのレースのどのレッグから出たか**を利用者が確かめられるようにする。
狙いは「数字を検算できる」ことと「振り返るべきレッグに辿り着ける」ことの2つ。読者は split 分析に慣れた上位層（`feedback_trails_results_analysis_rigor`）なので、**表示した数字とソースが1件でもずれたら信頼を失う**。

## 2. 現状と制約（実測・コード確認済）

- カードの入力 `public/data/leg-fingerprint.json`（本番 2.9MB）は**セル集計（n, m, flag）だけ**を持つ。レース・レッグ単位の出所はビルド時に捨てている（`leg-fingerprint.ts:513-544` の `RacePool` はセル番号とミス可否の配列だけで、レース識別子もレッグ番号も持たない）。
- 集計の定義（Stage 2b）:
  - ミス判定: `loss ≥ max(FLOOR, 0.30×(lap−loss))`（FLOOR は forest 10s / sprint 5s）
  - 局面: コースをレッグ番号で3等分する（`floor(3l/L)`、`:530`）
  - レッグ長: **同じレース内**の Ave3 基準所要時間で3区分する。閾値は**パック除外前の有効レッグ**から作り、閾値と同じ値は上の区分に入る（`:503-511`）。そのため「短い1/3」は厳密には正しくなく、**おおむね**1/3 になる。
  - 除外対象: リレー/フォーク系（名前で判定）・同姓同名・パック（集団走）レッグ・レースゲート（パックが過半、またはクリーンレッグが6未満のレース）
- 規模（DB 集計、2026-09-30）。パック除外とレースゲートを適用する前の**上限値**:

| | 対象選手 | 全レッグ | ミス判定レッグ | 1人あたりミス判定 p50 / p90 / max |
|---|---|---|---|---|
| forest | 1,519 | 1,004,452 | 177,512 | 78 / 249 / 1,628 |
| sprint | 646 | 151,753 | 18,712 | 23 / 52 / 196 |

- **ビルドは例外を握りつぶす**（`build-analysis-index.ts:1582-1591`）。途中で失敗すると、古い集計と新しい明細が混ざったまま公開されうる。
- **出走行を一意に特定できない**: tracked 行の取得列に `runner_index` が無い（`:1543`）。結果分析ページも主役を氏名で探して最初の一致を採る（`LegAnalysisClient.tsx:54-64`）。そのため同じクラスの再走（練習会など）や同姓同名を区別できない。
- 結果分析ページは `/results/<lc_event_id>/<lc_class_id>?athlete=` で開けるが、**既定は「主役＋上位3名」の比較表示**（`LegAnalysisClient.tsx:111-118`）で、特定レッグへのスクロールや強調の機能は無い。
- 更新は週1（水曜ビルド）。カードと同じビルドで生成しないと数字がずれる。

## 3. 設計原則

1. **一致の保証（最重要）**: 明細は、カードの集計を作るのと**同じループ・同じ判定**から書き出す（純関数 `buildLegFingerprintIndex` が集計と明細を同時に返す）。
2. **世代の一致**: 集計と明細は同じ世代 ID を持つ。UI は世代が一致しない明細を表示せず「更新中」と出す。混ざった状態を利用者に見せない。
3. **断定しない**: 個々のレッグを「あなたのミス」と呼ばない（方法論 §92）。赤フラグは**セル全体に対する**統計判定（permutation＋BH＋効果量）であり、個々の行には統計判定が無いことを見出しで明示する（§378）。
4. **定義と分母を見せる**: 局面・レッグ長の定義をパネルに書く。ミス判定でない行も出して、m/n を検算できるようにする。
5. **カード本体は重くしない**: 明細はセルを初めて開いたときに選手別ファイルを遅延取得する。

## 4. 仕様（v2）

### 4.1 データと生成
- tracked 行の取得列に `runner_index` を追加する。レースの識別は `(選手キー, lc_event_id, lc_class_id, runner_index)` で行う。
- **実装で変更（2026-09-30）**: 当初は「集計を明細から計算する（二重実装にしない）」としたが、既存の集計コードは**書き換えず**、同じループで明細（`RacePool` に legIdx/lap/loss/raceIdx を追加）を書き出す方式にした。理由: 既存カードの数字が変わらないことを実データで byte 単位に保証できる（変更前後の index が 2,958,398 byte で完全一致）＋集計と明細の2経路を突き合わせるほうが片方のバグを検知できる。一致は次の2つの検証で保証する:
  - `verifyFingerprintDetails`: 明細から数え直したセル n/m・規模別・ミス率・レース数・有効/除外レッグ数・期間別（表示ゲートの有無まで）が集計と一致するか。各レッグのミス判定と局面も再計算
  - `verifyDetailsAgainstSource`: 明細の各レースが元データ（tracked 行）の1行に特定でき、日付・大会名・クラス・レッグ数・種目が一致し、各レッグのラップ・想定との差が元の同じ番号のレッグと一致し、レッグ長の区分を元データから独立に再計算しても一致するか（Codex レビュー: 集計と明細が同じ配線バグを共有すると1つ目だけでは素通りするため）
- 除外情報: ゲートで不採用になったレース（理由 `x: pack|clean`）、スタート時刻不明のレース（`pu`）、パック除外したレッグ `[raceIdx, legIndex]` も記録する。
- 出力: `public/data/leg-fp/<gen>/<key>.json`（選手別・列指向 JSON・`.gitignore` 済み）。独自の固定幅符号化は使わず、圧縮は HTTP の gzip/Brotli に任せる。**manifest は作らない**（世代番号 `gen` は `leg-fingerprint.json` 自体に持たせる。別ファイルにすると公開時に揃える対象が増えるだけのため）。`gen` は generatedAt のミリ秒まで。
- **公開手順**: 集計と明細を作る → 2つの検証を全件で通す（書き出し前）→ 明細を書く → 集計（gen 付き）を一時ファイル＋rename で最後に書く。途中で失敗しても集計は git の旧版（gen なし）のままで、UI は明細を出さない。
- **失敗時の扱い（§7 判断 6・再確認中）**: Vercel のビルドは毎回 git から作り直すため、「前の世代」はビルド環境に無い。今の `keepOrSkeleton` が残すのは **git に入っている 2026-07-08 時点のスナップショット**で、失敗すると本番のカードが黙って 7 月の数字に戻る。一方、Vercel はビルドが失敗すると**前回成功したデプロイを本番に残す**。
  - **DB 取得後**（集計・2つの検証・書き出し）の失敗はすべてビルドを落とす（`FingerprintInvariantError` / `LegFpPublishError`）。ファイル名にできない選手キーも、何も書かずに落とす
  - DB 取得の一時失敗・行数不足ガード: 今の挙動（git のスナップショットに戻る）を踏襲し、明細は世代不一致で非表示。git スナップショットが古いこと自体は別件の課題（§5）
- 計測（実データ smoke・2026-09-30）: 掲載 1,388 選手・明細 1,388 ファイル・計 19.6MB（p50 8.4KB / p90 32.4KB / 最大 208KB・gzip 42KB）。生成 8.5 秒・検証 0.5 秒・書き出し 0.2 秒。Vercel の出力ファイル数制約上も問題なし（Codex 確認）。日本語ファイル名の実配信は PR の Preview で確認する。

### 4.2 UI（カード側）
- セルまたは重大度バーをタップすると、グリッド直下に**インラインパネル**を展開する（モーダルにしない）。選択したセルには枠を付ける。再タップか×で閉じる。button 要素にして aria-expanded を付け、キーボードでも操作できるようにする。
- **用語（2026-09-30 ユーザー決定）**: オリエン界隈では「ロス」という言い方をしないため、UI では使わない。機械的に引っかかったレッグは「**ミス判定**」と呼ぶ。秒数は「想定より +45秒（+38%）」のように事実だけを書く。カード本体の脚注などにある「ロス」4か所（`LegFingerprintCard.tsx`）も今回の PR で言い換える。結果分析ページなど既存ページの「ロス」（約40か所）は別件で洗い出す。
- 見出し: 「中盤×短レッグ　ミス判定 12 / 38 レッグ」。n<5 のセルは率を出さず「データ不足（2 / 4）」とする。
- 定義の1行: 「中盤＝コースのレッグを3等分した中央。短レッグ＝同じレース内の基準所要時間でおおむね短い1/3」
- 統計の1行: 「赤いセルは、このセル全体が自分の平均より偏って多いという判定です。個々のレッグに統計的な判定はありません」
- 一覧: **既定はレース日付の新しい順**（同じレースの行はまとめる）。「想定との差が大きい順」への切り替えもできる。20件ずつ「もっと見る」で全件まで辿れる。
  - 行の内容: 日付 ／ 大会名（省略表示）／ クラス ／ レッグ `6→7`（`S→1`・`14→F` 表記・全15）／ ラップ ／ 想定より `+45秒`（`+38%`）／ 規模（小・中・大。カードの「ミスの規模別 件数」と同じ区分）
  - 想定より速かったレッグは差がマイナスになる（実データで確認）。「想定より 6秒速い」と書き分け、`+-6秒` のような表記にしない
  - 行をタップすると結果分析ページへ移動する（同じタブ）: `/results/<ev>/<cls>?athlete=<key>&ri=<runnerIndex>&leg=<legIndex>&disc=&d=&cn=`
- 「ミス判定なし 26 レッグ」は折りたたみで、同じ行形式で出す。
- 集計対象外（折りたたみ・2段目）: 不採用レースは理由付きで一覧にし、パック除外は件数を出す。個別レッグは展開したときだけ出す。
- 注記: 「ミス判定は、想定タイムを30%以上上回ったレッグの機械判定で、ナビゲーションのミスとは限りません（地形・集団走・ルート選択を含みえます）。コースの難所かどうかは各レースのレッグ分析で確認できます。」
- 状態: 読み込み中／失敗（再試行ボタン）／世代不一致（「データ更新中」と出して行は表示しない）／連打した場合は最後に押したセルを採用する。

### 4.3 UI（結果分析ページ側）
- `ri` と `leg` を受け取ったら、`runner_index` で出走行を特定する（氏名一致より優先。見つからなければ今の氏名一致に戻し、その旨を表示する）。
- `leg` 指定のときは**その選手1人の表示**で開き、描画が終わったら該当レッグまでスクロールして一時的に強調する。
- レッグの表記（`S→1` / `k→k+1` / `N→F`）を両ページで同じ関数から作る。
- 結果分析ページで開けるかどうかはビルド時に分からない（LapCenter 側の削除など）。行は常にリンクし、開けない場合は結果分析ページの既存のエラー表示に任せる。

## 5. スコープ外（第2段階の候補・優先順）
1. 各ロス判定レッグに「同じクラスの他の選手もロスしたか」（フィールド中央値との比較）を付ける。companions の elapsed からラップの中央値は出せるが、他の選手の loss を得るには取得列の追加が要る。
2. セルを選んでいないときに「想定との差が大きいレッグ上位」を常に表示する。
3. 期間（直近12ヶ月／それ以前）で一覧を絞り込む。
4. （別件）DB 取得の一時失敗で、カードが git の古いスナップショット（2026-07-08）に戻る問題。最後に成功した生成物を Supabase Storage に保存して復元する等。
5. （別件）結果分析ページなど既存ページの「ロス」表記の洗い出し（約40か所）。
6. 対象外: 「クロスレース分析 — ミス率の相対評価」（`CrossRaceCard`）は別カードで、今回は触らない。

## 7. ユーザー判断（2026-09-30 決定）
1. **決定**: 行の語は「ミス判定」（「ロス」は界隈で使わないため UI から外す。既存ページの「ロス」は別件）
2. **決定**: 分母の行（ミス判定なしのレッグ）も折りたたみで出す
3. **決定**: 除外はレース単位の理由と件数を出し、個別レッグは2段目にする
4. **決定**: 結果分析ページの `?leg=` 対応（1人表示＋スクロール）を今回含める
5. **決定**: フィールド比較は第2段階の最優先
6. **決定（再確認済）**: 不変条件違反ならビルドを落とす（本番は前回成功デプロイのまま）。当初推奨の「前世代を残して通知」は、Vercel では前世代がビルド環境に無く「7月のスナップショットに戻る」になるため撤回（§4.1）。DB 取得の一時失敗は今の挙動を踏襲
7. **決定**: 一覧の既定は日付の新しい順。「想定との差が大きい順」に切り替え可
