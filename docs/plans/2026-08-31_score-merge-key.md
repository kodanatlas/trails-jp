# 過去の大会得点が引き継がれず消える問題（scoreMergeKey）

- 作成: 2026-08-31 18:58 JST
- ステータス: **調査完了・方針決定待ち（未実装）**
- 発見の経緯: 同姓同名分離（`2026-08-31_athlete-identity-layer.md`）のレビュー中に派生して発覚。本件は同姓同名とは**独立した既存バグ**

## 1. 何が起きているか

JOY のランキング API は**直近およそ1年分の大会得点しか返さない**。それ以前の得点は、ビルド時に既存ファイルからマージして引き継いでいる（`scripts/build-analysis-index.ts`）。

```ts
/** 既存スコアのマージキー（同姓同名の衝突回避のため所属も含める） */
function scoreMergeKey(e: { athlete_name: string; club: string }): string {
  return `${e.athlete_name} ${e.club}`;   // ← club は生文字列
}
```

`club` に**生文字列**を使っているため、所属の表記が少しでも変われば旧データが引けず、**1年より古い得点が黙って消える**。

JOY の所属欄には学年が入る（`東北大学2`・`筑波大学4` 等）ため、**進級のたびに必ずキーが変わる**。

## 2. 実測（2026-02-25 版と 2026-06-19 版の比較・4月の進級を挟む）

コミット `7627819`（2月）と `dd702b4`（6月）の `public/data/rankings/*.json` を直接比較した。

### 2-1. マージキーの不一致

| 区分 | 行数 |
|---|---|
| 6月版のうち、生文字列キーで2月版と一致しなかった | **3,681** |
| うち**所属を正規化すれば一致した**（＝この修正で救われる） | **410（11.1%）** |
| どちらでも一致しない（実際に所属が変わった） | 3,271 |

救われる例: `吉田聖悟 / 東京大学4`、`直江隼輝 / 筑波大学4`、`島倉大門 / 筑波大学3` — いずれも学年数字のみの差。

### 2-2. 実害（履歴の切り詰め）

「最古イベント日が前に動いた＝履歴の先頭が失われた」で測った。

| | 人数 | 最古イベント日の前進（中央値） | 60日以上前進した割合 |
|---|---|---|---|
| 所属文字列が変わった | 1,396 | +20日 | **36.0%** |
| 所属文字列が同じ | 3,229 | 0日 | 23.3%（ベースライン） |

ベースラインの23%は、JOY が上位N大会で集計するため**正常に起こる入れ替わり**。超過分の約13ポイントが本バグに由来する。

**決定的な個別事例**（意味的に同一の所属なのに履歴が消えている）:

```
奈良崎有香: 横浜国立大学 4 → 横浜国立大学4   最古 2025-03-08 → 2026-03-14  (+371日)
青木由奈:   早稲田大学3   → 早稲田大学4     最古 2025-03-08 → 2026-03-14  (+371日)
日比野兼伸: 名古屋大学院4 → 名古屋大学大学院4  最古 2025-03-08 → 2025-11-23  (+260日)
```

奈良崎の例は**空白の有無しか違わない**。正常な入れ替わりでは説明できない。

### 2-3. 規模

現行データで**所属が数字で終わる選手は 229名（全1,684名の13.6%）**。学生が大半のため、毎年4月に同数規模でキーが壊れる。

## 3. なぜ club がキーに入っているのか

コメントに「同姓同名の衝突回避のため」とある。氏名だけをキーにすると、同姓同名の別人の得点が混ざるため。

**ただし 2026-08-31 に改名シム（`src/lib/identity/athlete-alias.ts`）を導入したため、この前提は変わった。** 検出済みの同姓同名は上流で別名に分離されるので、マージキーが club を持つ必要性は下がっている。

## 4. 方針の選択肢

| | 内容 | 救われる行 | リスク |
|---|---|---|---|
| **A** | club を正規化してキーに使う（`normalizeClubName` + `splitAffiliations` + 順序統一） | 410 / 3,681（11%） | 低。正規化後に同一クラブとなる同姓同名だけが混ざる（現状でも混ざる） |
| **B** | キーを氏名のみにする | 3,681 / 3,681（100%） | 中。**未検出の同姓同名**の得点が混ざる |
| **C** | A を実施し、将来 B へ移行 | 段階的 | — |

### 推奨: B（氏名のみ）を本命、ただし前提条件つき

A は所属変更（転部・卒業・移籍）で消えるケース 3,271行を救えない。**選手が club を変えても本人の履歴は本人のものである**以上、club をキーに含めること自体が誤りに近い。

B の唯一のリスクは未検出の同姓同名だが、実測では**同一ランキング内に同名2行が現れる選手は 1〜2名**（鈴木健太・井戸康）しかおらず、うち鈴木健太は分離済み。井戸康は同一クラブのため A でも B でも混ざる（＝ A の優位性がない）。

→ **B を推奨する。** ただし下記を前提条件とする。

1. 同姓同名の検出器（同一ランキング内の同名重複）をビルド時に走らせ、**新規検出時に警告を出す**
2. 検出された名前は alias 表へ登録して分離する（既存の仕組みを使う）
3. 未登録の検出があるうちは、その名前**だけ** club 込みキーにフォールバックする

## 5. 未確定（実装前に決める）

1. **A / B / C のどれを採るか**（推奨は B ＋ §4 の前提条件3点）
2. **既に失われた履歴を復元するか**。git 履歴（`7627819` 以降）に旧ファイルが残っているため、部分的な復元は可能。ただし 2026-02-25 より前は残っていない
3. **`event_scores` の欠落を検知する仕組み**を入れるか（ビルド時に「前回より得点数が減った選手」を数えて警告する等）
4. 修正の適用タイミング。**次回の JOY 取得ビルドで上書きされる前に**入れないと、その回の履歴も失われる

## 6. 実装時の注意

- `scoreMergeKey` は `fetchCategory` 内で `existing`（旧ファイル）と `allFresh`（新規取得）の両方に適用される。**両側で同じキー生成を使う**こと
- 改名シム（alias）が先に適用された後の名前でキーを作る。順序を逆にしない
- クラブ正規化を使う場合は `src/lib/club-normalize.ts` の `normalizeClubName` / `splitAffiliations` を使い、再実装しない（同等の別実装が `leg-ingest.ts` 等に存在する既知の問題がある）

## 7. 受入条件（案）

- 2026-02-25 版と 2026-06-19 版のフィクスチャで、**マージキー不一致が 3,681 → 0（B の場合）または 3,271（A の場合）**になること
- 一般選手の `event_scores` 件数が修正前より**減らない**こと（全選手で機械照合）
- 同姓同名（`鈴木健太（筑波大学）`・`鈴木健太（金沢大学）`）の得点が互いに混ざらないこと
- `npx tsc --noEmit` / `npx vitest run` が clean
