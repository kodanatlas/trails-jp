# sync-lapcenter の maxDuration を 60s → 180s へ引き上げる

- 日付: 2026-09-09（JST）
- ステータス: **実装完了・デプロイ待ち**
- 関連: `2026-09-09_cron中断検知.md`（区分 C 方式。実装後に revert したため、本件はその代替アプローチ）

## 背景

`sync-lapcenter` の欠測（直近 60 日で 6 日 ≒ 10%）の原因が「未起動」か「60 秒キルによる中断」か
区別できない問題に対し、当初は開始記録 + watchdog 区分 C で**切り分ける**方式を実装したが revert した。

本件はそれとは逆の方針で、**切り分けるのではなく原因そのものを潰す**。

## データ根拠（直近 90 日・91 実行）

| 指標 | 値 |
|---|---|
| 平均実行時間 | 39.2 秒 |
| 45 秒超 | 20 回（22.0%） |
| 50 秒超 | 11 回（12.1%） |
| **55 秒超** | **6 回（6.6%）** |
| 最大 | 59.4 秒（2026-08-30。`maxDuration=60` の直前） |
| **`stopped_for_budget=true`** | **91 回中 90 回（98.9%）** |

読み取れること:

1. **60 秒キルの縁に頻繁に接近している。** 55 秒超が 6.6% で、欠測率（約 10%）と近い水準。
   しかもキルされた日は `logCron` に到達せず記録が残らないため、この 91 件には**現れない**。
   実際の分布はさらに右に裾が伸びているはずで、6.6% は下限値。
2. **ほぼ毎回、予算切れで取り込みを打ち切っている。** 候補 40 件（`MAX_RUNNER_EVENTS`）に対し
   実処理は 1〜14 件で、取込のバックログが恒常的に残っている。これは欠測とは独立した機能上の損失。

## Vercel の制約（2026-08-24 版ドキュメントで確認）

fluid compute（デフォルト有効）での上限:

| プラン | デフォルト | 最大 |
|---|---|---|
| Hobby | 300s | 300s |
| Pro / Enterprise | 300s | 800s（Beta で 1800s） |

現行の `maxDuration = 60` は Hobby の上限の 1/5 しか使っていない。
（60 という値は、fluid compute 以前の Hobby 上限 60 秒に由来すると思われる）

課金面: fluid compute の課金は **Active CPU 時間**が基準で、**I/O 待ちの間は停止**する。
本ジョブの実行時間は大半が mulka2 への HTTP 待ちと `DELAY_MS` のスリープなので、
壁時計時間を延ばしても費用増は限定的。

## 変更内容

`src/app/api/cron/sync-lapcenter/route.ts` のみ。

| 定数 | 変更前 | 変更後 | 理由 |
|---|---|---|---|
| `maxDuration` | 60 | **180** | キルの縁から離す。上限 300 に対しても余裕を残す |
| `START_EVENT_BEFORE_MS` | 30_000 | **120_000** | 着手期限。完走余裕 60 秒は最多クラス数 70（`DELAY_MS=300` で 21 秒）でも足りる |

`DELAY_MS = 300`（クラス間スリープ）は**変更しない**。総リクエスト数は増えるが、
mulka2 への間隔は従来どおり保たれる。1 日 1 回のジョブである点も含め、礼儀の水準は維持する。

`logCron` を通知より先に置く順序も**維持**する。着手期限を延ばした分、終端は依然として上限に近づきうるため。

## 未確定事項・デプロイ後に確認すること

1. **fluid compute が有効か。** ドキュメントは「enabled by default」とするが、
   古いプロジェクトでは無効の可能性がある。無効なら Hobby の上限は 60 秒のままで、
   `maxDuration = 180` はビルド時に弾かれるか、実際には 60 秒でキルされる。
   → デプロイ結果で判明する。失敗したら 60 に戻すか、ダッシュボードで fluid compute を有効化する。
2. **実行時間がどこまで伸びるか。** 着手期限 4 倍により、バックログ解消中は 120〜180 秒に達しうる。
   数日後に `cron_log.duration_ms` を確認し、180 秒の壁に当たっていないかを見る。
3. **`stopped_for_budget` が false になる日が出るか。** 出れば候補 40 件を消化しきったことを意味し、
   バックログ解消の指標になる。
4. **欠測が止まるか。** 60 秒キルが主因だったなら欠測率は下がるはず。
   1 ヶ月ほど様子を見て、なお欠測が続くなら原因は起動側（Vercel のスケジューリング）と切り分けられる。
   その場合は `2026-09-09_cron中断検知.md` の区分 C 方式を再検討する。

## 注意

本変更は「60 秒キルが欠測の主因である」という**仮説に基づく対処**であり、原因を確定させたわけではない。
確定させる手段（開始記録 + 区分 C）は revert 済みで、本変更でも「起動したか」は依然として観測できない。
ただし仮説が外れていても、`stopped_for_budget` の解消というもう一つの実利は確実に得られる。
