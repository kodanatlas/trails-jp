## 1. 巡航速度・ミス率カードに最新大会が反映されない（千葉大大会） — `97b2344`

### 症状
選手ページ(`/analysis`)の巡航速度・ミス率カード(`LapCenterChart`)に、実際の最新レース
「2026-06-06 第30回千葉大大会」(Forest)が出ない。順位推移・大会参加状況カードには出る。

### 原因
カードのロジックは正常で、`lc_performances` テーブルに当該レースの行が無いだけだった。
LapCenterスクレイプ(`sync-lapcenter`)が当該イベントを取得できていなかった原因は複合:
- **スループット不足**: `MAX_RUNNER_EVENTS=3` かつ水曜のみ実行＝週3件。マッチ済959件に対し
  取得済432件＝約527件未取得で、新しいレースが数年遅れの行列に埋もれていた。
- **巨大イベントの全損**: 旧実装は全行をメモリに貯めてループ後に一括upsert。`maxDuration`未設定で
  32クラスの千葉大大会(9827)に当たると関数が時間切れ→その回の全イベント分が0件保存。
- **processedKeys取りこぼし**: 処理済み判定が `select(...).limit(10000)`。2万行超のテーブルで
  キーが約半数欠落し、取得済みイベントを再取得して枠を浪費していた。

### 対応
- **即時バックフィル**: LC9827(第30回, 342名想定→338行)・LC9596(第29回午前, 2026-02-21)を
  `scripts/backfill-lapcenter-events.ts`（新規）で `lc_performances` に直接upsert。
  本番確認: 2026-06-06 千葉大大会 338行、`/api/lc` が最新点として返すこと、児玉健ほかの表示を確認。
- **恒久修正**(`sync-lapcenter/route.ts`):
  - `export const maxDuration = 60`
  - 水曜限定を撤廃して**毎日実行**
  - upsertを**イベント単位の逐次保存**に変更＋**壁時計予算ループ**(`START_EVENT_BEFORE_MS=30s`)で
    巨大イベントのタイムアウト全損を防止
  - `processedKeys` の取得上限 `10000`→`100000`
  - 候補上限 `MAX_RUNNER_EVENTS` 3→40（実処理数は予算で決まる）
  - 本番トリガーで `events_processed=2, db_inserted=59, stopped_for_budget=true` を実測

### 補足（レビューで確認・棄却した点）
- 別コンテキストのレビュアー2体で診断・方針を検証（CodexはChatGPTアカウントのモデル制限で
  headless実行不可だったためClaudeサブエージェントで代替）。
- 「JOY優先ソート」「クラス上限」はゴールドプレーティングとして不採用（逐次保存で代替）。

## 2. 応援ボタンの週次リセット — `1b2829e`

### 症状
応援ページの応援ボタンが一度押すと永続的に押せなくなる。

### 原因（2層の永続ブロック）
- **サーバ**: `likes` の一意制約 `(session_id, athlete_name)`＝1セッション1選手につき一度きり。
- **クライアント**: `localStorage` の応援済みフラグ（値 `"1"` 固定・期限なし）。

### 対応（JSTの週＝月曜起点でリセット）
- **DB**(`supabase/migrations/20260610_likes_weekly_reset.sql`・Management API経由で本番適用済み):
  一意制約を `(session_id, athlete_name, date_trunc('week', created_at AT TIME ZONE 'Asia/Tokyo'))`
  に変更。IPベースの日次連打抑止 `likes_ip_athlete_day_idx` は維持。
- **クライアント**(`src/lib/session.ts`): `hasCheeredGroup/setCheeredGroup` をJST月曜起点の
  週バケットで判定し、翌週に「応援済み」表示を自動リセット（サーバ境界と一致）。
- 仕様: 一意制約の週境界＝Postgres `date_trunc('week')`＝月曜00:00 JST。応援数は累積（ゼロ化しない）。

## 3. sync-lapcenter マッチング失敗の非致命化 — `39dcd10`

`sync-lapcenter` の `matchLapCenterEvents`(mulka2取得)が一時失敗すると cron 全体が error 化し、
エラーメール通知＋当日のスクレイプ全スキップになっていた。マッチングは `sync-events` でも毎日
実施・永続化されるため、`try/catch` で非致命化し、ストア済みマッチでスクレイプを必ず続行する
ようにした（`sync-events` と同じ方針）。`result.matching` にエラーをネストして可視化。

## 4. mulka2.com の証明書チェーン不備への対応 — `3155c6d`

### 原因
mulka2.com が **2026-06-06 にTLS証明書を更新**し、チェーンが不完全（中間CA「Let's Encrypt YR2」の
発行元が辿れない）になった。curl/ブラウザは AIA でチェーンを補完するが Node(undici) は AIA 非対応で
`unable to get local issuer certificate` となり、**Vercelからの mulka2 取得が全失敗**
（イベントマッチング・巡航速度/ミス率スクレイプ）。チェーン送出がサーバ間で不安定なため断続的に発生。

### 対応
`src/lib/scraper/lapcenter.ts` の mulka2 fetch(3箇所)を `undici` の専用 dispatcher
`new Agent({ connect: { rejectUnauthorized: false } })` 経由に変更し、**mulka2接続のみ**証明書検証を緩和。
公開成績データの取得のみで認証情報を送らないため影響は限定的。`package.json` に `undici` を明示追加。
- ローカルで `NODE_TLS_REJECT_UNAUTHORIZED` 無し・厳格TLS下でも 169イベント/32クラス取得を確認。
- 本番トリガーで `lc_events_fetched=2463`・scrape復活を確認。
- **mulka2 がチェーンを直したら、元の厳格検証に戻してよい**（コードにコメント済み）。

## 5. cron稼働の自動監視（クラウド定期エージェント）新設

`/schedule`(RemoteTrigger)でクラウド定期エージェントを作成。秘匿情報を使わず、Supabaseの
**公開anonキー**(RLS読取専用)で `cron_log` と `lc_performances` を毎日チェックし、**異常時のみ**
`kodan1126@gmail.com` にGmail通知する。

- ルーチンID: `trig_017n7Jko3feKQLNMrFwQsTWp`（管理: https://claude.ai/code/routines/...）
- スケジュール: 毎日 04:00 UTC(13:00 JST)
- 対象: **sync-lapcenter / sync-events / sync-entries** の3ジョブ
- 判定（持続的異常のみ・単発の一時失敗は許容）:
  - A: 最新ログ>30h（cron停止/障害）
  - B: 直近2件が連続で「失敗」。sync-lapcenterはハードニング済のため `status` だけでなく
    `result.runners.error`/`result.matching.error` も見る。
  - C: `lc_performances` 最新 event_date が28日以上前 かつ 直近runにscrape error → データ滞留
  - D: anonクエリ非2xx（キー失効/スキーマ変更）

### 検知の2層構成（最終形）
- **Resend（組込み・即時）**: `status=error` の即時通知＋ `high_empty_dates` 等のwarningカナリア。**残置**。
- **監視ルーチン（Gmail・日次）**: Resendが拾えない「無音失敗(success化)」「cron完全停止」「データ滞留」
  「キー失効」を補完。

## 残課題 / メモ

- mulka2 のTLS緩和（`rejectUnauthorized:false`）は、mulka2 がチェーンを修正したら厳格検証に戻す。
- 応援の「週次」は固定週（月曜JST）。ローリング7日にしたい場合はサーバを時刻ベース判定に要変更。
- sync-events/sync-entries は一時失敗でResend即時通知が鳴りうる。煩ければ sync-lapcenter 同様に
  ハードニング可（現状は genuine error のみで未対応）。
- ローカル `.env.local` の `SUPABASE_SECRET_KEY` は失効済み。ローカルからのDB読書は
  `SUPABASE_ACCESS_TOKEN`（Management API）経由で行う。
